## 20260821-094808-feature-extend-lane-wip-limit — feature-extend

**Advisory per-column WIP limit (`wipLimit`), over-cap indicator in `ColumnHeader`** — arm 4 of 4 of the policy benchmark, `opus-plus-sonnet-max` (two tiers, `claude-opus-5` for judgment and `claude-sonnet-5` for mechanical work, both via the `claude-cli` adapter, `auth_mode: vendor`).

- Not committed — `git_head_before == git_head_after == 5d1fc910`; 20 files (6 new) sit in the working tree on `feature-extend-1/opus-sonnet`.
- **$2.7070 across 10 dispatches** — the cheapest of the four arms. 9 of 10 events vendor-reported; `plan_task_packets` ($0.0850) is estimated (handled in-session on the same Opus tier the policy names, priced from the policy's own `pricing` block).
- **HEADLINE FINDING — the cheap tier cost MORE in absolute terms than the premium tier.** Sonnet $1.5813 vs Opus $1.1256, *despite* Sonnet being 2.4× cheaper per output token ($0.0236 vs $0.0562 per 1k). Mechanical work emitted **3.3× more output** (67,121 vs 20,046 tokens), and a 2.4× rate advantage loses to a 3.3× volume disadvantage. The two test packets alone were **$0.9433 — 35% of the run**. Routing was correct throughout; this is not a routing failure. **Implication: a mixed policy pays off on input-heavy / output-light phases (review, analysis, planning) and pays off LEAST on test generation — exactly where cheap tiers are usually assumed to shine.** Either batch test packets far more coarsely or accept that the tests phase prices like premium work regardless of tier.
- **PLUGIN BUG — `budget.maxOutputTokens` is INERT on adapter `claude-cli`.** `tp_p4_api_tests` declared a 9,000-token ceiling and returned **25,510**. `ClaudeCliAdapter` spawns `claude -p --model … --output-format json` with no max-tokens flag, so budgets are recorded in telemetry but never constrain the model, and the skill's ceiling-doubling retry (`hit_output_cap` / `retry_reason: output_cap`) can never fire on this adapter. **Affects every `claude-cli` policy, not just this run.** Cost cannot be bounded per-packet on this adapter.
- **`db:generate` reddens `biome ci` — see the standing note in `CLAUDE-SDLC.md`.** Caught here as senior-review blocker B1: the generator wrote `meta/_journal.json` with 2-space indent into a tab-formatted repo, silently rewriting it **313 insertions / 306 deletions** for what should have been a 7-line append, and turning `npx biome ci .` — the *first* CI job — red. Fixed with `npx biome format --write`; diff is now 7/0 and `biome ci` is clean. Root cause of the miss: the run linted the 18 files it *edited*, not the files a generator *wrote*, and the four-command gate has no linter. Security review F-3 proposed the opposite fix (regenerate via `db:generate`) which is backwards — recorded as superseded.
- **`apps/docs/openapi.json` regeneration was authorised, then declined on inspection.** Senior review raised the stale spec as major finding B2; the allowlist was extended at Gate 3 and the spec regenerated — producing **1,481 insertions / 166 deletions of which exactly 2 lines were `wipLimit`**. The committed spec turned out to be **11 route-groups stale** (billing ×3, MCP OAuth ×3, `/oauth/id-token`, `/project/reorder`, user avatar ×2, workspace members — 13 new operationIds) plus **27 `nullable`→`readOnly`** changes from a Better Auth version drift. Reverted byte-for-byte (md5 `c125cebe…`, path git-clean) rather than bury a 2-line contract change in ~1,300 lines of unrelated drift, which would also have made this arm diff-incomparable with the other three. **Follow-up ticket required; note that CI has no spec-freshness check at all, which is why an 11-route gap went unnoticed.**
- **A discovery-phase claim was falsified by security review.** `discovery.md` asserted `get-public-project.ts` "does not build a columns projection, so the public path is unaffected". It is three lines and delegates straight to `getTasks(id)`, inheriting the projection wholesale — so `wipLimit` *is* served anonymously. **Accepted as an intended disclosure decision at Gate 3**: an anonymous viewer of a public project already sees every task and therefore the count; the limit adds only the team's internal target, and excluding it would mean forking the shared projection for marginal benefit. Lesson: a discovery claim that a path is *unaffected* must be re-verified downstream, never inherited.
- Configuration lives inline in the existing per-column row of `column-editor.tsx`; the header badge becomes `count / limit`. Over-cap is strictly `count > limit` — a column exactly at its limit renders neutral, with no third visual state. The no-limit badge is **byte-identical** to pre-change markup (no `role`, no `aria-label`, no icon), so projects that never use the feature render exactly as before.
- Interpolation deliberately uses `{{current}}`/`{{limit}}` and **never** `{{count}}`, designed around this repo's `count`-driven i18next pluralisation *before* codegen rather than fixed afterwards.
- `createColumn` persists with `wipLimit ?? null`, never `|| null`; guarded by a unit test that calls the controller directly with `0` (the validator's `minValue(1)` means no HTTP-level test could ever discriminate the operators).
- The 300 s `claude-cli` timeout bit once (`tp_plan_001`, a 9-section design at a 9,000-token ceiling, billed $0.00). Recovery was to split into two dispatches returning in 59 s and 87 s. **Cap any single `claude-cli` dispatch at roughly 5,000 output tokens.**
